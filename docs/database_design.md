# Проектирование базы данных Cloud Application

## 1. Назначение базы данных
База данных предназначена для постоянного (persistent) хранения информации об облачных сервисах приложения Cloud Application, их типах и истории изменений состояний. Переход от хранения данных в оперативной памяти (`services_data` в Python-списке) к СУБД PostgreSQL обеспечивает сохранность данных при перезапуске сервера приложений.

---

## 2. Сущности и их атрибуты

### 2.1. Сущность `ServiceType` (Тип сервиса)
Служит для нормализации данных и исключения дублирования названий категорий/типов сервисов.

* **`id`** — уникальный идентификатор типа сервиса (Primary Key).
* **`name`** — название типа сервиса (например, `application`, `database`, `monitoring`).
* **`description`** — краткое описание назначения данного типа.

### 2.2. Сущность `Service` (Облачный сервис)
Основная сущность, представляющая отдельный облачный сервис.

* **`id`** — уникальный идентификатор сервиса (Primary Key).
* **`name`** — название сервиса (например, `Web Service`, `Database Service`).
* **`type_id`** — внешний ключ, ссылающийся на `ServiceType.id` (Foreign Key).
* **`status`** — текущее состояние сервиса (`running`, `maintenance`, `stopped`).

### 2.3. Сущность `ServiceStatusHistory` (История состояний сервиса — Самостоятельное задание)
Служит для ведения аудита и истории смены статусов сервисов.

* **`id`** — уникальный идентификатор записи истории (Primary Key).
* **`service_id`** — внешний ключ, ссылающийся на `Service.id` (Foreign Key).
* **`status`** — зафиксированное состояние сервиса.
* **`changed_at`** — дата и время изменения состояния (`TIMESTAMP WITH TIME ZONE`).

---

## 3. Связи между сущностями

1. **`ServiceType` ─── (1:N) ───> `Service`**
   * Один тип сервиса может соответствовать нескольким сервисам (например, несколько сервисов могут иметь тип `application`).
   * Каждый сервис принадлежит строго одному типу (`type_id`).
   * Связывающее поле: `Service.type_id` → `ServiceType.id`.

2. **`Service` ─── (1:N) ───> `ServiceStatusHistory`**
   * Один сервис может иметь множество записей об изменении статуса в истории.
   * Каждая запись истории относится строго к одному сервису.
   * Связывающее поле: `ServiceStatusHistory.service_id` → `Service.id`.

## 4. Логическая модель данных (PostgreSQL)

### Таблица `service_types`
| Поле | Тип данных | Ключ / Ограничения | Назначение |
| :--- | :--- | :--- | :--- |
| `id` | `INTEGER` | `PRIMARY KEY` | Уникальный ID типа |
| `name` | `VARCHAR(50)` | `NOT NULL`, `UNIQUE` | Название типа |
| `description` | `VARCHAR(255)` | `NULL` | Описание типа |

### Таблица `services`
| Поле | Тип данных | Ключ / Ограничения | Назначение |
| :--- | :--- | :--- | :--- |
| `id` | `INTEGER` | `PRIMARY KEY` | Уникальный ID сервиса |
| `name` | `VARCHAR(100)` | `NOT NULL` | Название сервиса |
| `type_id` | `INTEGER` | `FOREIGN KEY` → `service_types(id)` | Ссылка на тип сервиса |
| `status` | `VARCHAR(20)` | `NOT NULL`, `CHECK` | Текущий статус сервиса |

### Таблица `service_status_history`
| Поле | Тип данных | Ключ / Ограничения | Назначение |
| :--- | :--- | :--- | :--- |
| `id` | `INTEGER` | `PRIMARY KEY` | Уникальный ID записи истории |
| `service_id` | `INTEGER` | `FOREIGN KEY` → `services(id)` | Ссылка на сервис |
| `status` | `VARCHAR(20)` | `NOT NULL` | Зафиксированный статус |
| `changed_at` | `TIMESTAMP WITH TIME ZONE` | `NOT NULL`, `DEFAULT NOW()` | Время изменения статуса |

---

## 5. Требования к целостности данных

1. **Уникальность идентификаторов:** `services.id`, `service_types.id` и `service_status_history.id` являются `PRIMARY KEY`.
2. **Обязательность ключевых полей:** Поля `name`, `type_id`, `status` не могут иметь значение `NULL` (`NOT NULL`).
3. **Ссылочная целостность:** 
   * Поле `services.type_id` должно ссылаться только на реально существующий `service_types.id`.
   * Поле `service_status_history.service_id` должно ссылаться только на реально существующий `services.id`.
4. **Ограничение допустимых значений (CHECK):**
   * `services.status IN ('running', 'maintenance', 'stopped')`.
5. **Уникальность имён типов:** `service_types.name` снабжено ограничением `UNIQUE` для предотвращения дублирования категорий.

## 6. Соответствие REST API и операций СУБД

Внешний REST API оперирует единым представлением сервиса (со строковым полем `type`), тогда как внутри БД данные разделены на `services` и `service_types`:

| REST API метод | Операция в БД |
| :--- | :--- |
| `GET /services` | `SELECT` с `JOIN` таблиц `services` и `service_types` |
| `GET /services/{id}` | `SELECT` конкретного сервиса с `JOIN` `service_types` по `id` |
| `POST /services` | `INSERT INTO services` (с предварительным получением `type_id` из `service_types`) |
| `PUT /services/{id}` | `UPDATE services` (обновление имени, `type_id` или статуса) |
| `DELETE /services/{id}` | `DELETE FROM services WHERE id = ...` |

## 7. Дополнительное задание: Сравнение вариантов проектирования

* **Вариант 1 (Без нормализации):** Хранение строки `type` непосредственно в таблице `services`.
  * *Плюсы:* Проще структура, не требуются `JOIN`-запросы.
  * *Минусы:* Высокая избыточность (дублирование строк), сложность добавления описаний типов, риск опечаток в названиях типов.
* **Вариант 2 (Выделение `service_types` — Выбранный вариант):**
  * *Плюсы:* Исключение дублирования данных, удобство добавления метаданных (описания), обеспечение единообразия имён типов через внешние ключи.
  * *Минусы:* Необходимость выполнения `JOIN` при выборке данных.
